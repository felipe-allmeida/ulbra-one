# Budgeting Module
**Purpose:** processos de *"Orçamento & Requisições"* — requisição → aprovação com controle orçamentário → adequação → projects. **O DADO de orçamento (célula mensal por CC×Unidade×competência) NÃO vive mais aqui: foi relocado para o Core como `CostCenterUnitBudget`, dono do `CostCenter` (AEL-830).** Este módulo consome o orçamento do Core por porta.
**Schema:** `budgeting`  ·  **UoW:** inject `IUnitOfWork` directly (no key — single non-keyed `AppDbContext`-backed UoW)
## Boundaries
- Belongs here: the `Requisition` aggregate (purchase requisition, `/requisitions`), the `Project` aggregate (accumulated spending ceiling, `/projects`) and the `BudgetAdjustment` aggregate (budget adjustment, `/budget-adjustments` — AEL-791). **The budget cell itself lives in Core** (`CostCenterUnitBudget`, `/cost-centers/{id}/unit-budgets`, `core:read/write`); the removed `Budget`/`/budgets`/`budgeting:*` are gone (AEL-830).
- **Controle orçamentário autoritativo (AEL-830):** `IBudgetControl` (`Application/BudgetControl/`) computa, por competência, orçado (célula do Core via `ICostCenterBudgetLookup`) × consumido (realizado dos `RequisitionPayment` + empenhado das requisições em pagamento) × previsto (fila). **Disponível = orçado − consumido, SÓ (AEL-844): o previsto/pipeline (triagem/complemento/aprovação) NÃO reduz o disponível** — só requisições que chegaram a pagamento (InPayment+) consomem; o pipeline vira a projeção "disponível após aprovação" nas telas. O `Approve` bloqueia estouro (`Requisition.BudgetExceeded`, 409) contra o disponível REAL — bloqueio DURO, sem override (um estouro se resolve por Adequação que levanta o teto). Painel: `GET /requisitions/{id}/budget-control` e `GET /requisitions/budget-control`.
- `Project` (AEL-792) = spending ceiling tracked **accumulated across the project's life**, not per competency (that's `Budget`). `CalculateMetrics(requisitionCosts, committedCosts, paidAmounts)` → `ProjectMetrics` (`Previsto` = Σ costs + `InitialConsumedValue` = projeção de todo o pipeline; `Realizado` = Σ paid + `InitialConsumedValue`; **`Saldo` = `BudgetLimit − consumo real`, onde consumo real = Σ `committedCosts` (só requisições InPayment+) + `InitialConsumedValue` — o pipeline NÃO derruba o saldo, AEL-844**; `IsOverCeiling` = `Saldo < 0`; percentages return 0 on a zero ceiling instead of dividing). `InitialConsumedValue` = pre-system spend, counted in **both** previsto and realizado so migrated projects aren't understated. Status `Active→Finished|Cancelled` (terminal; no reopen). Requisitions link via the nullable `Requisition.ProjectId` (`LinkToProject`/`UnlinkProject`, guarded by `EnsureEditable` — Draft/Complement only). Cost per requisition reuses `Requisition.TotalCost()` (Biweekly = value × count/2) rather than re-deriving it. **Delete is blocked when requisitions are linked** (409 `Project.HasRequisitions`) — cancel instead, since `ProjectId` is a loose Guid with no FK to cascade. `Realizado` = Σ **real payments** fed back from Finance (AEL-793 outbox → `Requisition.RealizedValue`) + `InitialConsumedValue` (the former `Paid`/`Finalized`-status proxy is gone).
- `Requisition` (AEL-788) = the expense-flow "head" document (types Compra/Prestação de Serviço/Conta Fixa/Recorrência/Project). Guarded **state machine** (Draft→Triage→Approval→Complement→InPayment→AwaitingFiscalDocument→Paid→Finalized, +Cancelled) via `RequisitionException`/`RequisitionErrors` (stable codes, mirrors `AccountingPeriod`); `MarkFinalized` (not `Finalize` — collides with `object.Finalize`). Per-company sequential `Code` (friendly display number, separate from the typed id) = max+1 with unique `(CompanyId, Code)` index + retry-on-`DbUpdateException` (the `PostJournalEntry` pattern), assigned at create. Competency window is **type-first** (`AppliesToCompetency` — Conta Fixa/Recorrência span the range regardless of estimate type; else Full = start only, Monthly = range; open-ended when `EndCompetency` null). `TotalCost` = payment-plan total (Biweekly = value × count/2). **Hard-delete, Draft only** (like `Budget`; real requisitions terminate as Finalized/Cancelled). budget panel = AEL-790; project link = AEL-792. **Finance outbox = AEL-793 (entregue):** `VendorId` + `FirstDueDate` obrigatórios na criação (fornecedor validado no Registry via `IVendorLookup`); ao entrar em `InPayment` (approve do Aprovador) publica `RequisitionApprovedForPayment` no EF outbox → o consumer do Finance cria **1** Payable (`Origin=Purchase`, dedup por `OriginRequisitionId` único, idempotente); `PaymentRegistered`/`PaymentReversed` voltam para `RequisitionPayment` (realizado real bruto-equivalente, `MarkPaid` ao quitar / reabre ao estornar). Cancelar a requisição propaga o cancelamento à Payable (AEL-855). `MarkFinalized`/`AwaitingFiscalDocument` ainda não são dirigidos (dependem de contabilização/NF).
- **Esteira de aprovação (AEL-789, remapeada AEL-841/842)** = role-governed transition endpoints under `/requisitions` (`submit`, `approve-triage`, `submit-financial-complement`, `return-for-complement`, `resubmit`, `approve`, `cancel`), each mirroring the `ApprovePayable` template. Fluxo: Draft →(submit)→ Triage →(approve-triage, Controladoria)→ FinancialComplement →(submit-financial-complement, solicitante informa parcelas + data de emissão)→ Approval →(approve, Aprovador)→ InPayment. Domain stays **state + value only**: `Approve(budgetExceeded)` é um bloqueio DURO só de orçamento (`Requisition.BudgetExceeded`), **sem alçada e sem override** — o Aprovador aprova sem limite; um estouro se resolve por Adequação. Every transition appends a `RequisitionTransition` (who/when/from→to, SLA base); the endpoint calls `uow.AddAsync(requisition.Transitions[^1])` **explicitly** — else EF's store-generated-key heuristic marks a set-key child appended to a *Modified* parent as Modified → 0-row `DbUpdateConcurrencyException` (same reason `PayablePaymentService` AddAsyncs its `Payment`). `IApprovalAuthority` (Common port, Identity adapter) e `User.ApprovalLimit` seguem vivos só para a **Adequação** (não para requisições). Role→permission mapping: `requisitions:triage` = Controladoria, `requisitions:approve` = Aprovador.
- **Adequação orçamentária (AEL-791)** = ajuste de teto depois de o orçamento estar definido, sob esteira própria **triagem → aprovação** (`budget-adjustments:triage`/`budget-adjustments:approve`), com **alçada** na aprovação final (reusa `IApprovalAuthority`, igual à requisição — hard block, `null`=ilimitado, `0` bloqueia). Três tipos (`BudgetAdjustmentType`): **Suplementação** (destino `+= valor`), **Redução** (destino `-= valor`), **Transferência** (mesma Unidade×CC, origem `-= valor`/destino `+= valor`, competências distintas). A aprovação/reversão muta o teto da célula do Core (`CostCenterUnitBudget.MonthlyLimit`) **no mesmo `SaveChanges`** via a porta `ICostCenterBudgetMutator` (adapter em `Infrastructure/Dimensions/`, guard `WouldGoNegative`; célula destino é criada se faltar, redução/origem exigem célula existente → `CellNotFound`). Eixo de competência preservado (AEL-830 — sem mudança de schema da adequação). Sem estado Draft (cria em `AwaitingTriage`, editável/excluível só aí); **reversão é transição** (`Approved → Reversed`, recompõe o teto), não hard-delete. Grava `StatusChangedAt` (create + cada `MoveTo`) p/ o SLA de estágio, como a Requisition (AEL-790). Auto-contido no Budgeting (sem mensageria). **Anexos ficaram como follow-up** — `Justification` + `Counterparts` (obrigatória exceto Redução) cobrem o racional. A trava "não abaixo do consumido" é do painel/AEL-790 (client-side, interino); o backend só garante teto não-negativo.
- **"Natureza" = `CostCenter` (Core)** — there is no `Natureza` entity. The ~8 legacy naturezas map to CostCenters. (Not to be confused with `LedgerAccount.Natureza` in Accounting, which is the 1–5 accounting classification.)
- Budget cell granularity (agora no Core, `CostCenterUnitBudget`): **CostCenterId × UnitId × Competency ("YYYY-MM")**, teto `MonthlyLimit`; unique on that triple; FK real intra-Core ao CostCenter/Unit. O "orçamento anual" do CC é o roll-up (Σ dessas células).
- Cross-module refs (`CompanyId`/`UnitId`/`CostCenterId`) are **loose Guids — no FK across schemas**. Requisition dimension validation on create goes through the `IBudgetDimensionLookup` port (`Application/Dimensions/`; adapter in `Infrastructure/Dimensions/` references `Core.Domain`, read-only) — agora **exige cobertura** (unidade ∈ `CostCenterUnit`, `Requisition.UnitNotInCostCenter`). Leitura/mutação do orçamento do Core via `ICostCenterBudgetLookup`/`ICostCenterBudgetMutator` (mesmo padrão).
- Does NOT belong: payables/payments/bank/CNAB (Finance), accounting (Accounting), vendors (Registry).
- Dependency rule: Domain → (Common.Domain only); Application → Domain + Common.Application (NEVER Infrastructure); Infrastructure → Application + Domain + Common.Infrastructure + Core.Domain (lookup adapter only).

- `Ulbra.One.Budgeting.Domain/Entities/{Requisition,RequisitionAttachment,RequisitionTransition,RequisitionInstallment,RequisitionPayment,RequisitionException,Project,BudgetAdjustment,BudgetAdjustmentTransition,BudgetAdjustmentException}.cs`, `Enums.cs`, `ProjectMetrics.cs`. **`Competency.cs` foi movido para `Common.Domain`** (usado por Core e Budgeting). **A célula `Budget` foi removida** (vive no Core: `Core.Domain/Entities/CostCenterUnitBudget.cs`). `Approve` recebe um `bool budgetExceeded` (o veredito de orçamento; sem override).
- `Ulbra.One.Budgeting.Application/Endpoints/{Requisitions,Projects,BudgetAdjustments}/…`, `Endpoints/Requisitions/BudgetControl/{GetRequisitionBudgetControl,GetDimensionBudgetControl}.cs`, `BudgetControl/{IBudgetControl,BudgetControlService}.cs`, `Contracts/{RequisitionResponses,ProjectResponses,BudgetControlResponses,AdequacaoResponses}.cs`, `Dimensions/{IBudgetDimensionLookup,ICostCenterBudgetLookup,ICostCenterBudgetMutator,IVendorLookup}.cs`.
- `Ulbra.One.Budgeting.Infrastructure/Database/Configurations/{Requisition,RequisitionAttachment,RequisitionTransition,RequisitionPayment,Project,BudgetAdjustment,BudgetAdjustmentTransition}Configuration.cs`, `Dimensions/{BudgetDimensionLookup,CostCenterBudgetLookup,CostCenterBudgetMutator}.cs`, `Messaging/RequisitionPaymentConsumer.cs`, `BudgetingModule.cs` (`AddBudgetingModule` registra os 4 ports/serviços).
- Typed ids in `Common.Application/Ids/`: `RequisitionId` (`req_`), `RequisitionAttachmentId` (`reqatt_`), `ProjectId` (`proj_`), `BudgetAdjustmentId` (`adeq_`). A célula do orçamento usa `CostCenterUnitBudgetId` (`unit_budget_`), dona do Core.
- Permissions: `requisitions:read`/`write`/`triage`/`approve`, `projects:read`/`write` e `budget-adjustments:read`/`write`/`triage`/`approve` (`Permissions.cs`). **`budgeting:*` foi removida** — o CRUD do orçamento usa `core:read`/`core:write`. Esteira role→cargo (AEL-842): `requisitions:triage` = Controladoria, `requisitions:approve` = Aprovador. Frontend: gestão de orçamento vive na tela do Centro de Custo (`web/src/pages/centros-budget.tsx`).
- Frontend (AEL-792): `web/src/pages/projects.tsx` (list + detail with the previsto/realizado stacked bar and the over-ceiling alert + form), route `/app/projects`, queries `useProjects`/`useProject`/`useProjectMetrics`/`useSaveProject`/`useDeleteProject`, `api.ts` types hand-written (the Budgeting slice isn't in the generated OpenAPI schema yet).
## Testing
- Unit: `dotnet test tests/Ulbra.One.UnitTests` (Requisition state machine + budget guard, `IBudgetControl` semantics, `CostCenterUnitBudget` guards, Competency parsing — no Docker).
- Integration: `dotnet test tests/Ulbra.One.IntegrationTests` (Testcontainers Postgres + `ApiFactory`; `CreateAdminClientAsync()`).
- After any mapping/entity change: `dotnet ef migrations add <Name> --project src/Ulbra.One.Persistence --startup-project src/API/Ulbra.One.Api --context AppDbContext` (never hand-write); migrations auto-apply at startup. Commit the snapshot.
